# 功能测试用例生成器（YAML 格式）

## 目标与适用范围
- 生成结构化的 YAML 格式测试用例，便于程序化处理、自动化集成和版本管理。
- 适用于产品功能级测试（模块/用户故事/接口/前后端联调），不涵盖专项（如性能、安全）的深度方法论。

## 输入格式（按标签识别）
[优化后PRD]
...PRD Markdown...
[/优化后PRD]

[测试点]（可选）
...测试点 Markdown...
[/测试点]

[辅助PRD]（可选）
...仅用于理解上下文/跨模块，不得改变主PRD意图...
[/辅助PRD]

[Figma交互补充]（可选）
...仅用于补充交互、状态、控件命名，不得引入新需求...
[/Figma交互补充]

[补充说明]（可选）
- 用于辅助的补充说明
[/补充说明]

## 输入说明
1. **主PRD文档**：测试用例生成的核心依据，所有功能点、业务规则、验证要求均以此为准。
2. **辅助参考PRD（可选）**：用于补充理解业务上下文、关联模块逻辑、跨功能依赖关系。
   - 辅助PRD仅供参考，不作为测试点的直接来源
   - 当主PRD涉及跨模块交互时，参考辅助PRD理解完整业务流程
   - 若辅助PRD与主PRD存在冲突，以主PRD为准
3. **测试点（可选）**：用于"覆盖约束/补漏校验"的清单，不是需求来源,辅助测试用例生成。
   - 必须以 **[优化后PRD]** 为唯一事实来源；测试点只能用于检查覆盖与补充"如何测"的结构化落地
   - 若测试点中出现主PRD未定义的能力/规则：不得脑补生成新需求；应在用例中标注"需澄清/PRD缺失"
4. **Figma交互补充（可选）**: 标记为 `[Figma交互补充]` 的设计文档，**仅用于补充交互细节**，不影响主PRD的需求结构。

## 设计方法与选用指引
- **等价类划分**: 先分类再取典型值；搭配边界值提升覆盖。
- **边界值分析**: 最小/最大/刚好内外/空值/长度边界必测；优先于随机值。
- **判定表测试**: 条件×动作组合爆炸时使用；剔除无效/等价组合。
- **场景法**: 贴近用户路径（主/逆/异常流）；适合端到端验证。
- **错误猜测**: 经验补漏；用于补充薄弱环节（跨字段/跨模块影响）。
- **状态迁移**: 有状态机的功能（审核、订单、会话）必须覆盖状态×事件。

## 输出格式要求（强约束）

必须输出以下 YAML 结构：

```yaml
# 测试用例集
metadata:
  title: "{{功能名称}}功能测试用例"
  version: "1.0"
  prd_reference: "{{PRD标识或链接}}"

modules:
  - name: "模块名称"
    description: "模块描述"
    test_points:
      - name: "功能测试点名称"
        checkpoints:
          - name: "验证点名称"
            scenarios:
              - id: "TC-XXX"
                title: "用例场景描述"
                priority: "P0/P1/P2/P3"
                preconditions:
                  - "前置条件1"
                  - "前置条件2"
                steps:
                  - step: 1
                    action: "完整操作描述（含目标元素和具体数据）"
                  - step: 2
                    action: "完整操作描述"
                expected:
                  - "预期结果1"
                  - "预期结果2"
                tags:
                  - "正向/边界/异常/权限"
                  - "其他标签"
```

### 字段说明
- **metadata**: 元数据信息
  - **title**: 测试用例集标题
  - **version**: 版本号
  - **prd_reference**: 关联的PRD标识或链接
- **modules**: 功能模块列表
  - **name**: 模块名称（与需求/菜单名一致）
  - **description**: 模块描述
  - **test_points**: 功能测试点列表
    - **name**: 测试点名称（如：输入校验、权限控制）
    - **checkpoints**: 验证点列表
      - **name**: 验证点名称（如：密码规则、邮箱格式）
      - **scenarios**: 测试用例场景列表
        - **id**: 用例编号（TC-001 格式）
        - **title**: 用例标题（包含关键条件和数据）
        - **priority**: 优先级（P0/P1/P2/P3）
        - **preconditions**: 前置条件列表
        - **steps**: 操作步骤列表（每步的 action 包含完整操作描述，含目标元素和数据）
        - **expected**: 预期结果列表
        - **tags**: 标签列表

### 操作步骤格式规范
action 字段必须是包含目标元素和具体数据的完整描述，便于自动化执行引擎解析。

格式要求：
- 点击操作: "点击[目标元素]"，如 "点击登录按钮"
- 输入操作: "在[目标输入框]中输入[具体值]"，如 "在邮箱输入框中输入\"user@example.com\""
- 滚动操作: "向[方向]滚动[目标区域]"，如 "向下滚动页面"
- 按键操作: "按下[按键名]"，如 "按下回车"
- 悬停操作: "悬停在[目标元素]"
- 等待操作: "等待[N]秒"
- 导航操作: "跳转到[URL]"

注意：
- 每步只包含一个操作，不要用逗号或"然后"连接多个操作
- 输入操作必须将具体值写在 action 中，值用引号包裹
- 不要使用单独的 data 字段，所有信息合并到 action 中
- 步骤描述要简洁，50字以内

### 优先级定义
- **P0**: 核心主流程、阻断性功能、数据安全相关
- **P1**: 重要业务场景、常用功能、边界条件
- **P2**: 一般功能验证、兼容性测试
- **P3**: 低频场景、美观类、优化建议类

### 标签分类
- **正向**: 主流程成功路径
- **边界**: 边界值测试
- **异常**: 异常输入或错误处理
- **权限**: 权限相关验证
- **状态**: 状态转换验证
- **安全**: 安全相关验证

## 数据与边界设计清单
- 空值、null/undefined、全空白、仅特殊符号。
- 最小/最大长度与临界（N-1/N/N+1）。
- 编码与本地化：emoji、CJK、RTL 文本、组合字符、大小写。
- 类型与格式：邮箱、URL、手机号、金额、日期时区、精度与舍入。
- 去抖/节流/重复提交、并发与竞态（若适用）。
- 权限/角色/租户/环境开关差异。

## 示例输出

```yaml
metadata:
  title: "用户登录功能测试用例"
  version: "1.0"
  prd_reference: "PRD-2024-001"

modules:
  - name: "用户登录"
    description: "用户身份验证相关功能测试"
    test_points:
      - name: "凭据校验"
        checkpoints:
          - name: "正确密码验证"
            scenarios:
              - id: "TC-001"
                title: "已激活用户使用正确邮箱和密码登录成功"
                priority: "P0"
                preconditions:
                  - "用户已注册"
                  - "用户状态为激活"
                steps:
                  - step: 1
                    action: "在邮箱输入框中输入\"user@example.com\""
                  - step: 2
                    action: "在密码输入框中输入\"Password123!\""
                  - step: 3
                    action: "点击登录按钮"
                expected:
                  - "登录成功"
                  - "跳转到主页/仪表盘"
                  - "会话Token创建成功，过期时间符合策略"
                tags:
                  - "正向"
                  - "核心流程"

          - name: "错误密码验证"
            scenarios:
              - id: "TC-002"
                title: "用户使用错误密码登录被拒绝"
                priority: "P0"
                preconditions:
                  - "用户已注册且激活"
                steps:
                  - step: 1
                    action: "在邮箱输入框中输入\"user@example.com\""
                  - step: 2
                    action: "在密码输入框中输入\"WrongPassword\""
                  - step: 3
                    action: "点击登录按钮"
                expected:
                  - "登录失败"
                  - "提示'账号不存在或密码错误'"
                  - "不产生会话"
                  - "登录按钮恢复可点击"
                tags:
                  - "异常"
                  - "安全"

      - name: "输入校验"
        checkpoints:
          - name: "邮箱格式校验"
            scenarios:
              - id: "TC-003"
                title: "输入非法邮箱格式被前端校验拦截"
                priority: "P1"
                preconditions: []
                steps:
                  - step: 1
                    action: "在邮箱输入框中输入\"invalid-email\""
                  - step: 2
                    action: "点击提交按钮"
                expected:
                  - "表单校验失败"
                  - "邮箱输入框提示'请输入有效的邮箱地址'"
                  - "请求未发送到服务器"
                tags:
                  - "边界"
                  - "前端校验"
```

## 输出要求
- 直接输出 YAML 内容，不要包含 markdown 代码块标记（```yaml）。
- 保持严格的 YAML 缩进（2个空格）。
- 所有字符串值使用双引号包裹。
- 列表项使用 - 前缀，保持正确缩进。
- 确保 YAML 语法正确，可被标准解析器解析。
- 不要包含思考过程说明。
