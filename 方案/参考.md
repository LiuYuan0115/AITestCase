明白：你主要测 **Web 网页产品** + **插件产品（content-script 注入到网页里，没有侧边栏）**。这种组合的 UI 自动化，最稳的落地方式是把系统拆成三层：

1. **计划层（自然语言 / 上传测试计划 → 结构化可执行 DSL）**
2. **执行层（Playwright/Selenium 执行 + 统一断言 + 证据采集）**
3. **自愈层（失败分类 → 证据 → locator/步骤修复 → 有限重试）**

下面我按“能直接做出来”的角度给你一套方案（Web + 注入式插件都覆盖），并给关键代码骨架。

## 一、Web + 注入式插件的自动化总体架构

### 1）两种运行模式（建议都支持）

* **纯 Web E2E**：直接测试站点功能（登录、下单、表单等）。
* **带插件 E2E**：启动一个带“unpacked extension”的浏览器，访问站点后验证：

  * 插件是否注入成功（DOM/浮层/按钮）
  * 注入后交互是否正确（点击、弹窗、网络请求、写入 storage、DOM 变化）
  * 插件对页面的“副作用”是否符合预期（不遮挡、不破坏点击、不重复注入）

> 重点：既然你现在没有侧边栏，那 **所有可测行为都发生在 page 里**（页面 DOM + 插件注入 DOM），这反而更适合 Playwright。

## 二、你要的 3 个需求，分别怎么实现

## 1）自然语言输入“想做什么” → 自动操作浏览器 → 验证 → 报告

### 推荐实现：自然语言先转成“计划 DSL”（而不是直接写 Playwright）

把 LLM 的输出限制成固定结构，比如：

```json
{
  "name": "Plugin inject smoke",
  "baseUrl": "https://example.com",
  "steps": [
    {"id":"1","action":"navigate","url":"/"},
    {"id":"2","action":"assert","assert_type":"element_visible","target":{"by":"css","selector":"[data-ext-root='1']"}},
    {"id":"3","action":"click","target":{"by":"css","selector":"[data-ext-root='1'] [data-testid='open']"}},
    {"id":"4","action":"assert","assert_type":"text_visible","assert_value":"Answer is ready"}
  ]
}
```

**执行器**负责把 DSL 转成 Playwright 真实动作 + 等待 + 重试 + 采证据。
**自愈器**只在失败时介入，修 locator / 加一步“关闭弹窗/滚动/等待”。

这样你就能做到：

* 用户一句话 → 计划 → 自动跑 → 自动出 report
* 同一个计划可以反复跑、回放、Diff

## 2）上传测试计划实现（测试计划文档/用例集 → 自动执行）

你可以支持两种输入：

* **Markdown 测试计划**（给人看的）
* **JSON DSL**（给机器跑的）

流程：

1. 上传 Markdown → LLM 转 DSL
2. 执行 DSL
3. 输出报告（Markdown），并把“失败点 + 截图 + 修复尝试”写进去

关键点：**计划必须可定位到页面元素**
所以你需要一个统一的 locator 规范（下面会讲）。

## 3）“有代码实现 UI 自动化，并有自愈性和鲁棒性”

自愈不是“万能修复”，它是一个**严格受控的重试系统**：

### 自愈闭环（建议固定为 2 次）

1. step 失败 → 采证据：

   * screenshot
   * 当前 URL
   * 页面可见文本/关键 DOM
2. 失败分类：

   * selector 找不到
   * 元素不可见/被遮挡
   * 页面没稳定（loading）
   * 新窗口/重定向
3. 让 LLM **只输出**：

   * 新 locator（优先 role/label/testid，其次 text，最后 css）
   * 或补充一个“稳定步骤”（wait/scroll/close dialog）
4. 重试（最多 2 次）→ 仍失败就落盘报告

## 三、Web + 插件注入场景的“定位策略”（决定鲁棒性的核心）

### 你应该给 Web 和插件都加“可测试钩子”

这点 ROI 极高，能把自愈需求砍掉一半。

#### 对 Web 页面

* 给关键控件加：`data-testid="login-submit"`、`data-testid="email"`
* 或者至少保证 aria role/name 稳定（`<button aria-label="Sign in">`）

#### 对注入式插件（强烈建议）

你完全控制注入 DOM，所以务必加：

* 根节点：`<div data-ext-root="1" data-ext-version="x.y.z">`
* 内部控件：`data-testid="ext-open"`, `data-testid="ext-result"` 等
* 注入成功信号：注入后立刻在 `document.documentElement` 上挂一个属性也行：

  * `document.documentElement.setAttribute("data-ext-injected","1")`

这样你的断言就特别稳：

* `assert element_visible [data-ext-root='1']`
* `assert element_count == 1`（避免重复注入）

## 四、Playwright：如何跑“带插件”的 E2E（无侧边栏的最佳方式）

> Selenium 也能做，但 Playwright 对等待、trace、网络、选择器更舒服。

### 1）启动带 unpacked extension 的 Chromium（MV3/注入都适用）

```python
from playwright.sync_api import sync_playwright

EXT_PATH = "/abs/path/to/extension"   # unpacked extension directory
USER_DATA_DIR = "/tmp/pw-user-data"

def launch_with_extension():
    with sync_playwright() as p:
        context = p.chromium.launch_persistent_context(
            USER_DATA_DIR,
            headless=False,
            args=[
                f"--disable-extensions-except={EXT_PATH}",
                f"--load-extension={EXT_PATH}",
                "--no-first-run",
                "--no-default-browser-check",
            ],
        )
        page = context.new_page()
        page.goto("https://example.com", wait_until="domcontentloaded")

        # 断言：插件注入根节点出现
        page.locator("[data-ext-root='1']").wait_for(state="visible", timeout=10000)

        # 点击注入按钮
        page.click("[data-ext-root='1'] [data-testid='ext-open']")

        # 验证结果
        page.get_by_text("Answer is ready", exact=False).wait_for(timeout=10000)

        context.close()
```

如果你们当前走的是 **CDP 连接已打开的 Chrome(9222)** 的方式，也可以继续，但“加载 extension”的控制力更弱；**带插件 E2E 更推荐 persistent_context + load-extension**。

## 五、注入式插件的“可测性设计”（不然你会很痛苦）

由于网页 JS 不能直接访问 `chrome.*`，你测试时最好给 content-script 做一个“测试通道”。

### 推荐做法：window.postMessage 测试通道（只在测试 build 打开）

content-script：

```js
// content-script.js
const isE2E = !!localStorage.getItem("__E2E__"); // 或用 build flag
if (isE2E) {
  window.addEventListener("message", async (e) => {
    if (e.source !== window) return;
    if (e.data?.type !== "E2E_CMD") return;

    if (e.data.cmd === "PING") {
      window.postMessage({ type: "E2E_ACK", ok: true }, "*");
    }
  });
}
```

Playwright 测试里：

```python
page.evaluate("""
  localStorage.setItem("__E2E__","1");
  window.postMessage({type:"E2E_CMD", cmd:"PING"}, "*");
""")
# 然后 wait 一个 E2E_ACK（可用 page.wait_for_event('console') 或轮询 window 变量）
```

这样你能稳定做：

* 判断插件注入成功
* 触发某些内部动作（比如刷新、清缓存、模拟权限通过）
* 不依赖 UI 文案（避免 i18n/文案变化导致测试挂）

## 六、自愈与鲁棒：你应该做的“工程化配置”

### 1）统一 Locator 优先级（强制）

建议 locator 解析器按以下顺序尝试（这就是你的鲁棒性来源）：

1. `data-testid` / `data-ext-*`
2. `get_by_role(role, name=...)`
3. `get_by_label / placeholder`
4. `get_by_text`（谨慎使用，建议 partial）
5. CSS（最后）

### 2）每一步都要做“稳定化包装”

* `wait_for_load_state("domcontentloaded")`
* click/fill 前：`wait visible` + `scroll_into_view_if_needed`
* 失败必截图 + 记录 URL + 收集页面可见文本片段

### 3）失败分类 → 针对性修复（自愈不是瞎试）

* 找不到元素：换 locator / 放宽匹配 / 等注入完成信号
* 元素不可见：滚动/关闭遮罩/等待动画结束
* 被遮挡：点击前 hover / 使用 `trial` 点击判定 / 点击父级
* 重复注入：先 assert root count == 1，再继续
