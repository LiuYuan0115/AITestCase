## 二、需求智能体接口设计

### 2.1 接口规范

**基础信息**
- **接口路径**: `/api/prd` (新接口，弃用原 `/ask`)
- **请求方式**: POST
- **Content-Type**: application/json
- **上下文管理**: 以 `sessionId` 维护同一会话上下文

### 2.2 请求参数

#### 首次调用（带图片）

```json
{
  "sessionId": "session_1122xx11",
  "code": "plugin_test_testprd",
  "type": "testprd",
  "params": {
    "text": "提取的PRD文本内容...",
    "pictureKeyList": [
      "https://img.justsolvely.com/questionImage/xxx.webp"
    ],
    "isImageSolve": true,
    "isImageByte64": true
  }
}
```

#### 后续调用（对话/编辑）

```json
{
  "sessionId": "session_1122xx11",
  "code": "plugin_test_testprd",
  "type": "testprd",
  "params": {
    "text": "当前PRD内容..."
  },
  "instruction": "删除用户登录模块"
}
```

### 2.3 参数说明

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| sessionId | string | ✅ | 会话唯一标识，用于上下文关联 |
| code | string | ✅ | Prompt 代码标识 |
| type | string | ✅ | 请求类型标识 |
| params.text | string | ✅ | PRD 文本内容 |
| params.pictureKeyList | string[] | ❌ | 图片 URL 列表（首次调用必传） |
| params.isImageSolve | boolean | ❌ | 是否带图处理 |
| params.isImageByte64 | boolean | ❌ | 图片是否为 Base64 格式 |
| instruction | string | ❌ | 用户指令（后续调用） |

### 2.4 响应格式

```json
{
  "status": "success",
  "sessionId": "session_1122xx11",
  "type": "query | delete | add | modify",
  "response": "操作结果描述（中文）",
  "newPrd": "修改后的完整PRD（仅编辑操作返回）"
}
```

## 三、上下文管理策略

### 3.1 上下文组成

```
┌─────────────────────────────────────────────────────────────┐
│                      上下文窗口 (~8K tokens)                  │
├─────────────────────────────────────────────────────────────┤
│  1. 初始 PRD 文本 + 提取图片                                  │
│  2. 全页截图 (CDN URL)                                       │
│  3. 用户指令历史 (按钮 + 输入框)                              │
│  4. AI 回复历史                                              │
│  5. 当前修改后的 PRD                                         │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 上下文优化策略

- **滑动窗口**: 保留最近 N 轮对话，超出部分压缩摘要
- **增量更新**: 仅传递变更内容，减少 Token 消耗
- **优先级排序**: PRD 内容 > 用户指令 > 历史对话

## 四、Prompt 设计规范

### 4.1 系统 Prompt 模板

```markdown
# PRD 智能助手系统提示

## 角色定义
你是一名资深产品经理和测试专家，擅长 PRD 分析、逻辑审查和需求优化。

## 输出规范
- **语言**: 必须使用中文回复
- **格式**: Markdown 格式输出
- **态度**: 专业、简洁、有建设性

## 指令分类与处理

### 1. 分析类指令（左侧聊天回复）
- 检测逻辑冲突
- 识别潜在风险
- 结构化输出功能点
- 回答用户问题

### 2. 编辑类指令（修改右侧 PRD，支持撤回）
- 删除指定模块/内容
- 增加新模块/描述
- 修改/优化现有内容

## ⚠️ 删除操作严格规则
1. **最小化删除原则**: 只删除用户明确指定的内容
2. **精确匹配**: 仔细识别目标模块/章节/段落
3. **完整保留**: 除指定删除外，其他内容必须完整保留
4. **宁少勿多**: 不确定时，少删比多删安全
```

### 4.2 指令识别逻辑

```typescript
// 指令类型判断
const classifyInstruction = (input: string): 'query' | 'edit' => {
  const editKeywords = ['删除', '删掉', '移除', '去掉', '增加', '添加', '新增', '修改', '更改', '优化'];
  const queryKeywords = ['检测', '识别', '分析', '列出', '什么是', '为什么', '如何'];
  
  if (editKeywords.some(k => input.includes(k))) return 'edit';
  return 'query';
};
```

## 五、本地 Agent Server 实现

### 5.1 技术栈

- **框架**: FastAPI
- **LLM**: OpenAI GPT-4o (via ZenMux)
- **浏览器控制**: Playwright + CDP

### 5.2 核心接口

```python
# agent_server.py

from fastapi import FastAPI, Body
from openai import OpenAI

app = FastAPI()

# ZenMux 配置
client = OpenAI(
    api_key="sk-ai-v1-xxx",
    base_url="https://zenmux.ai/api/v1"
)

# PRD 智能体工具定义
prd_tools_schema = [
    {
        "type": "function",
        "function": {
            "name": "analyze_prd",
            "description": "分析PRD文档，必须用中文回复",
            "parameters": {
                "type": "object",
                "properties": {
                    "analysis_type": {
                        "type": "string",
                        "enum": ["conflict", "risk", "feature_list", "question"]
                    },
                    "result": {
                        "type": "string",
                        "description": "分析结果（中文 Markdown）"
                    }
                }
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "edit_prd",
            "description": "修改PRD文档，只删除用户明确指定的部分",
            "parameters": {
                "type": "object",
                "properties": {
                    "action": {
                        "type": "string",
                        "enum": ["delete", "add", "modify"]
                    },
                    "description": {
                        "type": "string",
                        "description": "操作描述（中文）"
                    },
                    "deleted_content": {
                        "type": "string",
                        "description": "被删除内容摘要"
                    },
                    "new_prd": {
                        "type": "string",
                        "description": "修改后的完整PRD"
                    }
                }
            }
        }
    }
]

@app.post("/api/prd_agent")
def prd_agent(payload: dict = Body(...)):
    """PRD 智能体主接口"""
    user_prompt = payload.get("prompt", "")
    current_prd = payload.get("prd", "")
    
    # 构建系统提示
    system_prompt = f"""你是PRD智能助手，必须使用中文回复。
    
当前PRD内容：
---
{current_prd[:8000]}
---

⚠️ 删除操作规则：只删除用户明确指定的部分，保留其他所有内容。
"""
    
    # 调用 LLM
    response = client.chat.completions.create(
        model="openai/gpt-4o",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt}
        ],
        tools=prd_tools_schema,
        tool_choice="auto"
    )
    
    # 处理响应...
    return {"status": "success", ...}
```

### 6.2 撤回机制实现

```typescript
// 消息结构
interface Message {
  role: 'user' | 'ai';
  content: string;
  actionType?: 'edit' | 'delete' | 'add' | 'query';
  canUndo?: boolean;
  undoData?: string;  // 修改前的 PRD
}

// 撤回操作
const undoPrdEdit = (msgIndex: number) => {
  const msg = messages.value[msgIndex];
  if (!msg?.canUndo || !msg.undoData) return;
  
  // 恢复 PRD
  projectState.documents.prd = msg.undoData;
  
  // 标记已撤回
  msg.canUndo = false;
  msg.content = msg.content.replace('可撤回', '已撤回');
  
  addMessage('ai', '↩️ 操作已撤回，PRD 已恢复。');
};
```

## 七、优化 PRD 的 Prompt 参考

```markdown
# 优化需求文档规则 (Optimize PRD Rules)

## 角色定义
你是一名资深产品经理，擅长梳理业务逻辑、完善边界条件以及撰写结构清晰的需求文档。

## 任务目标
接收用户提供的 Markdown 格式需求文档（主）和需求文档截图（辅），输出一份格式优化且逻辑更严谨的 Markdown 需求文档。

## 输入说明
1. **Markdown 文档**: 需求的主要内容来源。
2. **全屏截图**: 辅助参考，主要用于理解需求文档大概的布局结构，防止出现标题和内容不符的情况，但不作为核心内容来源。

## 处理规则

### 1. 格式与层级优化 (Format & Hierarchy)
- **标题重构**: 调整 Markdown 的标题层级（H1-H6），使其逻辑结构清晰、父子关系明确。
- **排版规范**: 统一列表样式、段落间距、加粗强调等，提升文档可读性。
- **结构化**: 确保文档包含清晰的模块划分。

### 2. 边界条件补充 (Boundary Analysis)
- **逻辑审查**: 基于 Markdown 内容，深度分析业务逻辑，识别未明确的边界条件。
  - *例如*: 输入字段的最大/最小长度、字符类型限制、空值处理、重复数据处理、状态流转的异常分支等。
- **截图辅助**: 仅参考截图的视觉布局理解需求文档大概的布局结构，防止出现标题和内容不符的情况，不要将截图中的所有文字（如菜单、页脚等无关信息）强制通过 OCR 添加到文档中。
- **补充方式**: 在原有逻辑基础上，以"补充说明"或直接融入功能描述的方式添加缺失的边界定义。

### 3. 约束事项 (Constraints)
- **禁止琐碎添加**: 不要因为截图里有而 Markdown 里没有，就强行添加无关的模块（如导航栏、版权信息等），除非它影响核心业务逻辑。
- **忽略视觉对齐**: 不需要描述截图的颜色、像素间距或具体 UI 样式，仅关注功能逻辑。
- **保持原意**: 优化仅限于格式梳理和边界补全，严禁修改原有的核心业务意图。
- **保留图片**: 必须保留原 Markdown 文档中包含的飞书文档图片链接（通常以 image 标签或 markdown 图片语法存在），保持其在文档中的相对位置。
- **新增高亮**: 在原有 PRD 描述基础上，以任何形式的新增，都高亮显示，如 `【新增补充】` 标注。

## 输出格式
请直接输出优化后需求文档的 Markdown 内容，不要包含思考过程说明。

## 模型配置
- 推荐模型: GPT-4o
- Token 限制: 约 8K 上下文
```

## 八、错误处理与容错

### 8.1 常见错误码

| 错误码 | 说明 | 处理方式 |
|--------|------|----------|
| AGENT_OFFLINE | 本地 Agent 未启动 | 回退远程 API |
| CONTEXT_OVERFLOW | 上下文超限 | 压缩历史对话 |
| LLM_TIMEOUT | LLM 响应超时 | 重试 + 提示用户 |
| INVALID_INSTRUCTION | 无法识别指令 | 引导用户重新输入 |

### 8.2 容错策略

```typescript
const handleAgentError = (error: Error) => {
  if (error.message.includes('fetch')) {
    // 网络错误：提示启动本地服务
    return '⚠️ 本地 Agent 未启动，请运行 ./run_agent.sh';
  }
  if (error.message.includes('timeout')) {
    // 超时：建议简化请求
    return '⏱️ 请求超时，请简化指令后重试';
  }
  return `❌ 处理失败: ${error.message}`;
};
```

# AI Test Case 测试用例智能体 - 技术方案

参考prompt：

# 功能测试用例规范指南

## 目标与适用范围
- 明确、统一功能测试用例的结构与质量门槛，兼容思维导图工具（如XMind）导入。
- 适用于产品功能级测试（模块/用户故事/接口/前后端联调），不涵盖专项（如性能、安全）的深度方法论。

## 术语与约定
- **模块**: 被测的功能单元（例如：用户登录）。
- **功能测试点**: 模块下的关注领域（例如：输入校验）。
- **验证点**: 某类规则或子能力（例如：密码规则）。
- **用例场景**: 单个可执行、可验证的测试。
- 本指南统一使用 H1~H6 结构；严格遵循下文结构要求以确保可被工具解析。

## 设计方法与选用指引
- **等价类划分**: 先分类再取典型值；搭配边界值提升覆盖。
- **边界值分析**: 最小/最大/刚好内外/空值/长度边界必测；优先于随机值。
- **判定表测试**: 条件×动作组合爆炸时使用；剔除无效/等价组合。
- **场景法**: 贴近用户路径（主/逆/异常流）；适合端到端验证。
- **错误猜测**: 经验补漏；用于补充薄弱环节（跨字段/跨模块影响）。
- **状态迁移**: 有状态机的功能（审核、订单、会话）必须覆盖状态×事件。

## 文档结构（强约束）
- 严格遵循如下层级。标题文字为内容，不加数字前缀。

```markdown
# [文档主标题，例如：XX功能测试用例]

## [功能模块名称]
### [功能测试点1，例如：头像设置]
#### [验证点1.1，例如：上传规则校验]
##### [用例场景1.1.1]
###### 预期结果
- 预期结果详情1
- ...
##### [用例场景1.1.2]
###### 预期结果
- 预期结果详情1
- ...
#### [验证点1.2，例如：默认逻辑校验]
##### [用例场景1.2.1]
###### 预期结果
- 预期结果详情1
- ...

### [功能测试点2，例如：昵称规则]
#### [验证点2.1，例如：格式规则校验]
##### [用例场景2.1.1]
###### 预期结果
- 预期结果详情1
- ...
```

## 元数据规范（建议，置于文末或文首说明段）
- **版本**: vX.Y（同需求/PR版本同步）。
- **关联需求**: 需求编号或链接。
- **覆盖范围**: 模块/API/页面清单。
- **设计方法**: 勾选使用的方法（等价类/边界/判定表/场景/错误猜测/状态迁移）。
- **数据依赖**: 账号、配置、开关、第三方依赖。
- **非功能约束**: 国际化/可访问性/权限/合规要点（若适用）。

## 命名与粒度规范
- **模块名（H2）**: 与需求/菜单名一致，避免缩写。
- **功能测试点（H3）**: 一类规则或能力，如“输入校验”“权限与可见性”。
- **验证点（H4）**: 单一规则主题，如“邮箱格式规则”“最大长度处理”。
- **用例场景（H5）**: 要包含关键条件、动作与特定数据，例如：
  - “已激活用户使用正确的邮箱和密码登录成功”
  - “昵称为256字符（超长）保存被拒绝并提示长度上限为64”
- **预期结果（H6）**: 可验证、可度量、可追踪到UI/接口/数据。
- 粒度建议：H5 每条为“单目标”断言，不混多主题；跨主题拆分。

## 数据与边界设计清单
- 空值、null/undefined、全空白、仅特殊符号。
- 最小/最大长度与临界（N-1/N/N+1）。
- 编码与本地化：emoji、CJK、RTL 文本、组合字符、大小写。
- 类型与格式：邮箱、URL、手机号、金额、日期时区、精度与舍入。
- 去抖/节流/重复提交、并发与竞态（若适用）。
- 权限/角色/租户/环境开关差异。

## 状态迁移与判定表示例（可内联为注释区块）
- 状态迁移最小覆盖：每个状态的所有有效事件×结果状态；无效事件应明确拒绝。
- 判定表最小覆盖：去重后保留每类动作的代表性有效/无效组合各1~2条。

```markdown
#### 状态迁移校验
##### 从“待审核”在“管理员批准”事件后进入“已通过”状态
###### 预期结果
- 状态更新为“已通过”，时间戳记录成功。
- 审计日志新增一条“审批通过”记录。
```

## 场景法补充建议
- 主路径：首次成功、重复成功（幂等）、恢复性（故障后重试）。
- 逆路径：中断/取消/回退、跨页面返回、刷新与直达链接。
- 异常路径：网络失败、服务超时、部分成功、降级提示。

## 可验证性与断言规范
- UI：提示文案需精确匹配（或使用稳定选择器/数据-testid），颜色/禁用态/按钮可点击性可验证。
- API：HTTP 状态码、响应体结构、关键字段、幂等等级。
- 数据：库内新增/更新/计数不变，时间戳/操作者/审计日志。
- 事件：埋点/消息/任务队列触发与否。

## 质量门禁检查清单（评审用）
- H1~H6 结构合法，未使用数字前缀；无空层级。
- H5 场景是否“单主题、含条件与关键数据”。
- 预期结果是否“可验证、可度量、可定位到界面/接口/数据”。
- 边界值、无效等价类是否覆盖；状态/判定表是否到位（若适用）。
- 权限/国际化/可访问性是否考虑（若适用）。
- 测试数据依赖是否明确；环境/开关注明（若适用）。

## 常见反例与修复
- 反例：H5 标题过泛，如“测试登录功能”。
  - 修复：写为“未激活用户使用正确凭据登录被拒绝并提示需激活”。
- 反例：预期结果笼统，如“显示正确”。
  - 修复：写明“提示文案为‘密码错误’，登录按钮恢复可点击”。
- 反例：混合多规则，如长度与字符集同案断言。
  - 修复：拆分为“长度上限校验”“非法字符拒绝”两条。

```javascript
async function executeTestCase(testCase) {
    const startTime = Date.now();
    const results = {
        id: testCase.id,
        name: testCase.name,
        status: 'running',
        startTime: startTime,
        steps: [],
        screenshots: [],
        errors: []
    };
    
    try {
        // 执行测试步骤
        for (const step of testCase.steps) {
            await executeTestStep(step, results);
        }
        results.status = 'passed';
    } catch (error) {
        results.status = 'failed';
        results.errors.push(error.message);
    } finally {
        results.endTime = Date.now();
        results.duration = results.endTime - results.startTime;
    }
    
    return results;
}
```

### 错误处理策略
1. **元素未找到**: 重试3次，等待时间递增
2. **网络超时**: 增加等待时间，记录网络状态
3. **页面崩溃**: 重新初始化浏览器，从失败点继续
4. **验证码识别失败**: 刷新验证码，最多尝试5次
